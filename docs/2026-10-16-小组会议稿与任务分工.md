3. 每项本轮任务都有主负责人、协作人、交付物、验收人和截止时间。

## 二、项目目前概述

目前项目分成三层：上面是 ArkUI-X 客户端和 Web 调试页面，中间是 FastAPI 后端，下面是 Agent、校园工具和数据库。模型负责理解问题、选择工具和组织回答；课表、地点、路线、教室等信息由工具提供；最终任务写入由后端业务代码处理。

现有 Agent 已经具备多轮文本对话和本地工具调用。它可以查询课程、校园地点等信息，也可以生成计划提案。用户确认后，后端再创建实际计划或待办。因此，我们演示时要同时看回答、工具结果、确认卡片和规划页面，不能只看模型说得是否完整。

还有几个概念先统一：目前工具tool主要是本地 Python 函数，部分通过普通 HTTP 请求 HDUHelp，这些还不等于接入了 ==MCP==，所以agent还有非常大的优化空间。聊天历史目前存在服务端 SQLite，也不等于客户端已经实现本地持久化，或者 Agent 已具备==长期记忆==。

### 三、本轮重点

现在的基础框架已经有了，接下来主要解决五类问题。

第一是界面和**可视化**。用户应该看得懂 Agent 查了什么、生成了什么、需要自己确认什么；计划不能只显示一部分又没有展开入口，地图和长文本也要适配手机屏幕。

第二是 Agent 的规划和运行控制。我们要检查它是否先查真实数据、是否正确处理缺少信息和时间冲突，以及失败后能否明确结束。不能只靠增加提示词来保证业务规则。

第三是**工具、MCP 、长期记忆和数据**。地图路线要核对真实道路（尝试接入地图api），天气目前还是演示数据；**MCP** 先做一个只读工具的最小闭环，证明真的完成了连接、发现和调用，再决定后续扩展。

第四是后端检查。重点看**安全性**方面：身份隔离、接口异常、计划确认和数据库写入，特别是任务修改删除、重复确认以及执行中途失败这些边界。

第五是鸿蒙和跨端交付。鸿蒙语音、本地会话历史、Android 和 iOS 的实际运行情况，都需要有人专项跟进。工程目录存在和设备实际跑通，是两个不同的验收结果。



下面我们按五条工作线认领。每条线先确定一位主负责人，再确定协作人；主负责人负责范围和交付，协作人负责约定好的接口或验证。

认领时请一起确认三个问题：这轮最先交付哪一项，依赖谁提供什么，以及在什么时间能拿出可运行的结果。如果一项任务明显超过一个人的时间，就拆成更小的子任务，不把“研究一下”当作最终交付。

## 五、新任务分工：五条工作线，负责人现场确认

优先级约定：**P0 为核心正确性与课题必交缺口；P1 为首轮扩展；P2 为后续增强。** 优先级不代表所有事项都能在一周内完成；会上只把有人员、工时和依赖保障的事项纳入本轮承诺。

### 开发与交付约定

- 每人按单一目的修改，提前约定 `tools.py`、`schemas.py`、`store.py` 等共享文件的接口与整合方式。
- 交付包含代码/文档、运行步骤、截图或录屏、实际执行的验证和未完成项；“研究了某项技术”只算阶段进展。
- 每次实际改动新增一份本地修改日志，记录涉及文件、实际验证和建议提交标题；保留已有本地工作。
- 提交前审查差异，执行 `git diff --check` 和相关检查；密钥、令牌、数据库、虚拟环境、IDE 配置和构建产物遵循现有忽略规则。
- 是否提交、推送、创建 PR 另按明确安排执行。`修改日志/` 当前仅本地保存；团队同步进度时另附脱敏摘要，不默认日志已经上传。
- API 错误码、字段或平台能力变化，应同步接口说明和前端，不让其他成员靠阅读实现猜测行为。
