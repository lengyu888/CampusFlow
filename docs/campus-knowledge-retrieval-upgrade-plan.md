# 校园知识检索扩展与优化方案

方案日期：2026-10-19，Asia/Shanghai。状态：方案，尚未实施。

用户已明确暂缓工具与 Skill 治理，下一项扩展校园知识检索。本方案复用现有 Agent、
运行预算、证据展示及 Skill 开关，不重做工具注册或权限体系。

## 1. 目标与首期范围

把当前“少量参考条目的短语匹配”扩展为可导入、可更新、可检索、可定位原文的校园知识服务。
回答应能说明依据来自哪份资料、哪个版本和哪个小节；资料不足时明确缺口。

首期继续面向杭州电子科技大学下沙校区的公开资料。推荐优先整理图书馆、校园网络、
常用学习与办事指南，目标约 20 份有实际内容和可核对来源的资料，包含现有四份。
新主题及具体来源需在资料采集阶段确认，不在本方案中假定校方页面已经存在或规则已经核验。
成功标准是实际问题覆盖率，不以凑够文件数量代替质量。

首期支持受控登记的 HTML 页面和人工整理的 Markdown/文本；第二步支持带文本层 PDF。
扫描 PDF、图片和复杂表格先标记待处理，后续再接 OCR。个人成绩、校园卡余额、
当日空教室等继续调用既有业务工具；资料检索不提供这些数据的实时替代品。
登录后校内资料、个人上传文档、跨学校知识共享、全网自动搜索、MCP 连接均另行设计。

## 2. 现状核对

| 当前实现 | 已有能力 | 本次需要解决的问题 |
| --- | --- | --- |
| `knowledge_sources.json` | 四个官方页面的人工整理条目及来源 | 只有少量摘要，不是原文分块知识库 |
| `knowledge.py` | NFKC 规范化、短语组匹配、校区过滤、最多三条 | 没有通用全文索引；条目数量还硬限制为3–6 |
| `_UNCOVERED` | 避免静态资料冒充实时状态 | “续借、借阅期限、账号激活”等也被整体排除，扩展后需要按资料覆盖和问题性质处理 |
| 知识 API、Agent 工具 | 直接查询与 Agent 查询可共用知识能力 | 数据导入、版本发布及更新尚无独立流程 |
| `tool_presentation.py` | 与随包静态条目逐项比对，防止伪造来源 | 动态结果和旧版本不能继续靠新建默认 `KnowledgeService()` 比对 |
| 原生知识面板 | 标题、小节、短摘录、链接、核对日期 | 客户端要求结果最多三条；需要显式兼容版本和片段详情 |

关键入口：`knowledge.py`、`knowledge_sources.json`、`tools.py`、`api.py`、
`tool_presentation.py`、`KnowledgePresentation.ets`、`CampusKnowledgePanel.ets`。

本次已对项目虚拟环境做内存 SQLite 探测：SQLite 3.45.3 支持 FTS5 与 trigram。
对“图书馆借阅规则”直接查询“图书馆/借阅/借阅规则”，unicode61 均未命中；
trigram 命中三个字以上的上述片段，但“借阅”未命中。
因此不能直接把默认 tokenizer 或 trigram 当作已经完成中文检索。
这是本机能力探测，不代表所有部署环境已具备相同 SQLite 功能。

## 3. 路线选择

| 路线 | 收益 | 成本与限制 | 建议 |
| --- | --- | --- | --- |
| 继续增加 JSON 和匹配词 | 最快增加少量固定问法 | 人工规则持续增长，原文、版本和同义问法仍受限 | 仅用于兼容迁移 |
| SQLite 版本化资料库 + 中文全文检索 | 与当前部署相近，可离线运行、容易定位来源 | 需要导入、分块、中文预处理及质量基线 | 首期采用 |
| 立即接向量库、embedding、重排模型 | 可能改善语义和同义表达召回 | 新模型、凭据、成本和部署依赖；效果仍需评测 | 词法基线后按缺口引入 |

保留现有“Agent 按需调用知识工具”的路径，直接校园资料搜索使用同一检索服务。
首期检索不依赖 LLM，不因每次搜索增加模型调用。该组合符合工具驱动检索的使用方式，
不要求切换现有运行框架。[LangChain Retrieval](https://docs.langchain.com/oss/python/deepagents/retrieval)

## 4. 建议数据流

```text
登记官方来源 / 提交已整理资料
  → 抓取或读取 → 提取正文 → 生成版本 → 按章节分块
  → 人工预览核对 → 构建候选索引 → 校验 → 原子发布

问题 + 服务端学校/校区 + 查询日期
  → 查询规范化与有限同义词扩展
  → 范围/版本/有效期过滤 → 词法候选召回与排序
  → 去重、证据完整性检查 → 在预算内装入完整片段
  → 直接结果 / Agent 回答 → 原文小节与版本详情
```

导入与在线查询分开。用户提问时不现场抓取整站，不让校园网页速度直接拖住 Agent 回合。
索引故障与真实零命中分别返回错误或缺失状态；不能把数据库不可用包装成“没有规定”。

## 5. 资料导入、版本与更新

来源登记保存：官方 URL、学校/校区、主题、发布部门、格式、读取方式及复核周期。
首期用仓库内可审查的来源目录和维护命令，不增加后台管理页面。
在线 API 只查询已发布版本，不能提交任意 URL 让后端直接抓取。

每份资料至少保存以下元数据：

| 对象 | 关键字段 |
| --- | --- |
| Document | 稳定 `document_id`、标题、来源 URL、学校/适用校区、主题、发布部门 |
| DocumentVersion | `version_id`、正文 hash、抓取/核对时间、原文发布日期、生效/失效日期、解析器版本、发布状态 |
| Chunk | `chunk_id`、所属版本、章节路径、段落序号、页码、原文字符范围、正文及内容 hash |
| CorpusRelease | 资料清单 hash、索引格式/分词版本、构建时间、校验结果、激活版本 |

未知发布日期或有效期记录为未知，不能用抓取时间填成规则生效时间。
学校级资料可明确标记适用于多个校区，不能把校区未注明直接当作所有校区通用。
初始登记的复核周期可按资料变动频率设置，复核到期不等于规则已废止。

同来源同正文重复导入不产生重复片段；内容变化才建立新版本。
新版本经过预览与索引校验后原子激活；查询期间不能读到新旧索引混合的半成品。
抓取失败保留上次成功版本并记录复核状态，不能把再次读取旧缓存标成刚更新。
已知失效或被替代的版本不进入当前问题的默认召回；明确历史问题另走历史版本定位。

首期“下架”停止新检索，并让历史引用显示下架/旧版本状态；历史问答和已保存运行快照
可能仍包含原先公开资料，不把下架宣称为全部副本已物理删除。
彻底删除、私有资料及其派生内容清理属于后续独立范围。

资料正文、数据库和构建索引放入已忽略的运行数据目录；提交来源清单、处理代码和必要的
小型脱敏测试样例。应用安装包需随附来源清单及初始化说明，不能依赖开发者本机索引才可运行。

## 6. 清洗、分块与中文检索

HTML 提取标题、正文和层级，去掉导航、页脚及重复模板；保留列表和表格语义。
正文按章节/条款优先分块，初始目标每块约500–900中文字符；过长段落再按句拆分，
必要时保留不超过100字符上下文。申请条件、例外、时间范围和表格行不能被随意截断。
片段正文与整理说明分开，摘要不得冒充原文；没有页码的 HTML 不虚构页码。

推荐首期检索配置：

- 标题、小节和正文分别建索引，标题与小节提高权重。
- 中文预处理生成相邻二字片段，英文缩写与数字保留为词项；原文另存，不把预处理文本展示给用户。
- 查询走相同预处理，添加少量可审查的同义关系，如“借书/借阅”；不给每道测试题写专属匹配规则。
- 对单字、纯停用词、极短宽泛问题要求补充含义或明确返回证据不足，不自动凑结果。
- FTS5 BM25 提供基础排序，配合原文短语命中、主题覆盖及重复片段去重；初始最多召回20个候选，保留前5个供评测与证据打包。
- SQL 使用参数绑定，FTS 查询表达式由受限词项构建；用户输入不直接成为 FTS 运算符。

分词和排序规则单独版本化。启动/构建前验证目标 SQLite 的 FTS5 能力；不支持时明确报告
配置问题，保留既有已发布版本，不假装索引初始化成功。
SQLite 官方说明了 tokenizer 与 BM25 的能力，并明确 trigram 全文查询无法命中不足三个字符的子串；
本方案采用预处理来补足中文短词，而非假定其原生中文分词已足够。
[SQLite FTS5](https://www.sqlite.org/fts5.html#tokenizers)

带文本层 PDF 可采用 pypdf 提取，保留页码并检查阅读顺序。提取为空或乱码应进入待处理状态，
不能发布成“无相关内容”。扫描 PDF 后续单独接 OCR 并人工抽样核对。
[pypdf 文本提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)

## 7. 证据、回答与实时信息边界

每个检索命中返回稳定文档/版本/片段标识、标题、小节或页码、原文片段、来源 URL、
核对日期和已知有效期。检索分数只用于排序，不展示为“答案正确概率”。
校区、发布状态和版本过滤在生成候选时应用；不能只查全库前几名后再过滤，造成漏召回。

Agent 应按片段作答，引用定位到实际使用的小节/页码；多材料要求与例外必须一起保留。
不同资料矛盾且无法确定适用关系时展示冲突，不能仅按抓取日期选一个当作正确规则。
搜到静态规则不代表实时开放、余位或个人办理状态已核验。

扩展后逐项替换 `_UNCOVERED` 的粗粒度排除：若语料确有借阅期限或激活流程，可以回答相应
静态规则；密码、余额和实时状态仍不从公共知识正文推断。
混合问题应分开处理，例如先根据规则资料回答借阅说明，再明确当前座位需要其他业务数据。
无证据时说明覆盖范围与缺失项，不能说学校没有该规定。

回答可使用服务端分配的片段引用编号。引用校验至少确认：编号属于本次运行实际向模型提供的
片段、版本及校区匹配、原文定位存在。编号合法并不证明模型陈述受到原文支持，语义支持仍需评审。
检索正文仅作资料，不能改写系统规则、授予权限或触发未确认写入。

## 8. API、客户端和运行预算

当前客户端知识搜索只接收最多三条结果，后端也采用严格 schema。本次不直接将它们改成
五个片段并假定旧端自然兼容。

建议保留 v1 查询/详情适配，并为完整片段结果提供 v2 契约：

- v1 保留原有字段、数量和旧来源 ID 的定位能力；现有四个条目可作为迁移种子。
- v2 返回文档分组、匹配片段、版本定位和覆盖提示；页面仍最多三张文档卡，每张可展开对应片段。
- `found/missing/unsupported` 与查询故障继续区分；故障用明确错误，不增加未被旧端识别的状态冒充成功。
- 来源详情按 `document_id + version_id + chunk_id` 定位；历史引用不能静默跳到新正文。
- Agent 的 `search_campus_knowledge` 工具名和既有 Skill 归属保留；工具结果、展示摘要、两端解码和历史回放同步支持新版本契约后再启用。

将 `tool_presentation.py` 的静态全量对象比对改为调用同一版本化证据仓库核验，避免
检索使用新库、展示仍只认旧四条 JSON 的分裂状态；过渡期支持已保存的 v1 轨迹。

每次仅向模型提供预算内的完整证据片段。打包上限须服从现有单工具结果限制和整轮上下文预算，
序列化后的 JSON 也计入大小。知识结果采用结构化裁减，保留必要引用元数据，不能被通用
字符串截断变成半个 JSON。引用登记以实际送入模型的片段为准，不以后台曾召回20条为准。
若连一个完整片段也放不下，明确提示缩小问题或预算不足。
旧 chat 的模型请求 middleware 继续检查实际发送大小；此处不扩大为通用工具治理改造。

## 9. 质量基线与验收

建立独立校园知识评测集，关联现有38场景基线，但不覆盖或修改旧报告。
初始建议80题，冻结资料发布版本与标准片段：40题库内事实/同义问法、10题多条件/例外、
10题错误校区/失效版本、10题实时信息/无依据、10题中文短词/编号/对抗资料。
其中至少20题保留为不参与调参的留出集。真实学籍、密钥和用户账户数据不进入题库。

以下为建议验收门槛，不是本轮测得结果：

| 检查 | 建议标准 |
| --- | --- |
| 当前范围、版本、生命周期与引用归属 | 固定控制用例全部通过；不存在跨校区误用或失效版本冒充当前资料 |
| Recall@5 | 对已标注可回答的题，至少90%在前5候选找到必要证据；多条件题另统计全部必要片段覆盖率 |
| 实际提供给模型的证据覆盖 | 单独统计预算打包后覆盖率，不能用后台候选召回率冒充 |
| 引用定位 | 固定用例全部可定位版本/片段；伪造编号不得当成合法引用 |
| 有依据回答 | 人工核对关键陈述与原文；建议至少90%关键陈述有支持，未知和遗漏另计，不拿模型自评作唯一依据 |
| 无依据处理 | 所列控制题不编造确定规则；未执行真实模型评审时记未评测 |
| 检索耗时 | 独立记录检索P50/P95，建议本机1万片段热索引P95不超过300ms；记录设备、题数和冷/热条件 |

先测试纯检索，再使用离线模型替身验证实际 Agent 工具输入、输出、引用和预算链路，
最后单独执行真实模型回答评审。构建成功、索引有数据或接口测试通过不代表知识回答质量达标。

## 10. 分阶段交付

| 阶段 | 实际交付 | 验收后再进入下一阶段 |
| --- | --- | --- |
| A：资料与全文检索底座，建议下一项先做 | 来源目录、导入预览、版本/片段库、中文词法索引、发布/回滚命令；现有四份迁移并逐步扩充 | 导入幂等、中文短词、校区版本过滤、失效/故障区分及固定检索集通过；现有API和客户端保持可用 |
| B：有出处的 Agent 与页面闭环 | v2片段契约、v1兼容、证据仓库校验、预算打包、引用定位、原生/Web展示适配 | 直接检索、Agent、新旧运行/历史、旧客户端兼容及真实模型评审分别记录结果 |
| C：按失败样本增加语义召回 | 独立embedding配置、词法+向量候选融合；必要时再引入重排 | 在同一冻结留出集上优于A/B基线，成本与延迟可接受，无范围/版本退化 |

阶段A是可独立审查的后端变更，不把整个知识系统一次性改完。阶段B完成后才称为原文检索回答闭环。
阶段C不预定向量库品牌，也不默认 DeepSeek 对话模型能提供 embedding；若启用，须单独确认
embedding 模型、凭据、数据发送范围和版本，不能直接复用个人 DeepSeek Key 给其他供应商。
没有明确评测收益时停留在词法方案。

## 11. 代码切入点与回滚

建议新增 `knowledge_ingest.py`、`knowledge_repository.py`、`knowledge_retrieval.py`，
逐步将现有 `knowledge.py` 保留为兼容入口；细分文件在实施计划中按实际规模确定。
新增来源目录与知识评测集，修改已有 API、工具结果、展示校验和知识页面；仅修改相关代码，
不顺带重排 Agent Runtime 或 Skill 架构。

知识库使用独立 SQLite 文件，避免为公开资料导入直接变更个人账户/任务数据库。
发布版本可回退到上一份经校验的索引和资料清单；应用回滚时保留 v1 适配及旧来源定位，
不通过整库重置覆盖账户、会话或计划。
每阶段均追加累计摘要和本地修改日志；提交、推送仍需用户明确要求，固定使用优化分支。

## 12. 本轮实际完成与验证边界

本轮只完成源码/契约核查、三份官方技术文档核对、本机内存 SQLite 功能探测和方案编写。
未新增资料正文、索引或依赖，未修改服务端/客户端运行代码，未执行完整测试或真实模型评测。
没有采集20份新资料，也没有验证候选校园主题的具体规定。
后续实施前以本方案作为范围依据，先细化阶段A的字段、命令和测试，不直接启动向量服务。
