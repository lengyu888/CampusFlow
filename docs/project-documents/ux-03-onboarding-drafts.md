# UX03：渐进引导与本机草稿恢复

本阶段在 UX02 的共享视觉基础上补充录课与输入恢复，仍沿用原有课表校验、导入预览和显式确认流程。以下验收为离线逻辑与静态工程检查；没有安装原生 SDK、没有原生编译、实机或模拟器运行，也没有调用真实模型。

## 首次录课

首次使用保留「校园与学期 → 添加真实课程 → 核对完整课表」三步。学校与内置校园地点仍为杭州电子科技大学下沙校区，不将现有资料套用到其他校园。

- 先展示课程名称、具体日期、开始和结束时间。地点、教师与连续周次放在可展开的补充信息中；默认只添加一次。
- 一门真实课程即可完成录课要求。模型、语音与提醒可稍后设置；引导不申请这些权限。
- 连续周次仍由用户明确选择，展开为具体日期；单双周、节假日不会被猜测。编辑仍只针对选中的那一次课程。
- 所有录课时间使用北京时间。草稿的基准日期保留；隔天恢复不会把原日期改成今天。
- 订阅地址只用于本次预览。未接受候选不进入持久草稿，接受后只存课程与来源提示，不绑定订阅。
- 全量课表仍按每页 10 条显示，使用全局索引；确认保存覆盖完整课表，不截断为当前页。

## 助手与待办

未发送的助手文字和未提交的待办可在同账号、同服务下恢复。恢复不会发送消息、重开旧会话、生成提案或新增任务。待办保存原本的明确日期和输入基准，跨日后仍显示原日期并提醒核对。助手恢复保留原输入日期，提醒用户检查相对日期。

助手提交前保存原运行 ID 与严格白名单的单次请求；待办确认前保存原提案 ID。查回服务器完整候选后仍需用户核对、明确确认。提交结果未知时不另建重复安排；发送之后新写的内容使用较新本机修订号，不被旧回执清除。旧时间选择器、后台回包和被删除会话的运行都不能把输入写回另一账号。

注册时模型配置可稍后进行。省略凭据会以未配置状态保存；使用模型时仍按真实服务状态提示配置。账号登录、校园配置和现有权限仍需完成。

## 本机草稿与账号边界

草稿文件格式版本为 1，最多 20 份草稿、40 个待核对操作，总文件最多 4 MiB、单份最多 2 MiB；300ms 防抖，后台和离页主动 flush。文件以同目录临时文件、完整 UTF-8 写入、fsync、rename 更新；坏文件不静默覆盖。通用草稿排除密码、模型凭据、原始音频、订阅地址和可执行提案。

共享存储通过 `DraftLease` 隔离服务地址和用户。两页使用各自的 `kind` 与 `ownerId = main`；凭据由既有认证流程处理，不进入草稿。

| 草稿内容 | 首次引导 | 日常课表维护 |
| --- | --- | --- |
| 已加入的课程、来源提示 | 保存 | 保存 |
| 六字段原始表单、当前编辑索引、连续周次、展开状态 | 保存 | 保存 |
| 尚不合法或未填完的输入 | 有界保存，不自动纠正 | 有界保存，不自动纠正 |
| 原基准日期与 `Asia/Shanghai` | 保存 | 保存 |
| 原服务端 revision 与基线课程 | 保存 | 保存 |
| 订阅 URL、未接受导入候选 | 不保存 | 不保存 |
| 待核对的保存 | 原操作指针与类型化冻结提交 | 原操作指针与类型化冻结提交 |

再次进入时先显示「恢复」与「舍弃」操作，不自动把旧输入填入新的写请求。恢复只回填本机内容。存在待核对保存时不能直接舍弃并另建提交；需先查原操作。

退出账号会清除本机草稿并同步使旧 lease 失效。旧页请求与迟到回调不能向新账号写入草稿或触发完成导航。本机落盘失败显示恢复入口；保存前必须成功落盘，不能把内存暂存宣称为已持久保存。

## 原版本与新版本的差异

恢复始终保留原 `expectedRevision` 和基线课程。联网读取到不同 revision 时显示账号最新课表，可逐页查看完整内容，并保留原草稿供核对。不会把旧草稿自动绑定到新 revision 后覆盖。

日常维护可明确放弃草稿并重新读取；读取失败仍保留旧内容。首次引导需明确舍弃旧草稿，再按最新配置重新录入。日期、地点和课程标题不作为服务端回执或成功判断的替代依据。

## 可靠保存与重启核对

日常课表维护沿用原 `operation_id + expected_revision` 协议。首次引导补充相同级别的幂等保存：

- `GET /api/v1/onboarding` 返回权威 revision、用户、课表与校园地图。
- `PUT /api/v1/onboarding` 在原正文上带成对的 UUID `operation_id` 与 `expected_revision`。
- `GET /api/v1/onboarding/operations/{id}` 查询原保存回执。
- 回执含原/新 revision、课程数、地点数和保存时间。客户端验证原操作标识与冻结内容的计数，再读取最新权威配置；只有查回当前已完成的配置才进入主界面。

客户端顺序为：冻结用户确认内容 → 本机草稿落盘 → 操作指针落盘 → 发送保存。网络断开、回执缺失、隐藏或重启都不会自动建立新 ID。恢复先查询原 ID；只有明确返回相应 `OPERATION_NOT_FOUND` 时，才提供由用户点击的「原标识与原内容重试」。重试不会重新抓取订阅或校园地点，也不会混入新的表单编辑。

成功核对后，原操作指针与其对应的同修订草稿在一次本机原子写中清理；较新的草稿保留，避免清理中断后把已提交内容再次当作新草稿。

过期基线被服务器拒绝后仍保留旧草稿；账号数据发生变化不能通过重新绑定版本绕过。已有成功回执但最新配置读取失败时只重试读取，不重复提交。

## 代码落点

- `pages/OnboardingPage.ets`：渐进表单、显式草稿恢复、原版本对照、首次保存回执核对。
- `pages/TimetablePage.ets`：日常维护表单持久化、原提交恢复、最新课表分页对照。
- `utils/TimetableMaintenance.ets`：独立导出与恢复快照、保存前持久化边界、原 operation 冻结与复用。
- `utils/DraftStore.ets`、`services/LocalDrafts.ets`：共享白名单快照、修订号、原子文件写入与操作指针；由共享存储实现负责。
- `pages/Index.ets`：登录 scope、退出清理、前后台 flush 与各页面 lease 接线；助手和待办接入同一存储。
- 后端账户服务与 API：首次配置 revision、SQLite 幂等保存与回执查询。
